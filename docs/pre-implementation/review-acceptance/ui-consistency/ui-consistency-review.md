# 企业级统一监控平台 UI 一致性评审验收

## 1. 评审结论

| 项目 | 结论 |
| --- | --- |
| 总体结论 | 有条件通过 |
| 是否适合进入设计稿绘制 | 可以进入核心排障链路和配置链路设计稿绘制；列表/状态页、视觉 token 与状态语义需先补齐口径 |
| 是否阻塞进入设计稿绘制 | 不整体阻塞；阻塞“全量页面设计稿一次性开画” |
| 主要原因 | UI 方向、排障优先级、权限边界、状态覆盖和组件体系基本成立，但跨文档存在少量规格不一致，以及产品原型中的列表/状态页面未形成同等粒度的高保真页面说明 |

本次评审认为，当前高保真 UI 文档整体符合企业级监控排障平台定位：专业、克制、高密度，强调异常定位、Trace ID 贯穿、日志/指标证据链、按应用授权与审计。可支撑核心页面先行绘制。

但在进入完整设计稿生产前，需要收敛以下问题：色彩 token 口径、告警级别与运行状态映射、按钮层级、导航尺寸、日志上下文默认值、接入/未知状态表达、列表类页面覆盖范围。

## 4. 问题清单

| 编号 | 严重度 | 问题 | 影响 | 建议修正 |
| --- | --- | --- | --- | --- |
| UI-CONS-01 | 中 | 基础视觉 token 跨文档不完全一致。视觉规范主文本为 `#1F2937`，核心页面写 `#111827`；分割线视觉规范为 `#DDE3EA` / `#E8EDF3`，核心页面写 `#E5E7EB`。 | 设计稿与前端 token 可能出现同类文本、边框深浅不一致。 | 以 `visual-system.md` 为唯一 token 源，核心页和配置页只引用 token 名称，不重复写散色值。 |
| UI-CONS-02 | 中 | 左侧导航宽度存在 216px 与 224px 两种说法。 | 页面栅格、表格宽度、折叠导航状态在设计稿中会漂移。 | 统一为 216px，或明确配置页采用同一全局框架，不单独设 224px。 |
| UI-CONS-03 | 高 | P0/P1 与“严重/异常”的颜色映射仍有局部混用。视觉规范中 P0=`#DC2626`、P1=`#EA580C`，但核心页面“危险”写 `#DC2626` 用于 P0/P1。 | 告警等级可判读性下降，尤其 P0/P1 在列表置顶和趋势图中可能难以区分。 | 明确：P0=严重/红，P1=异常/橙红，P2=预警/黄橙，P3=信息/蓝；文档中避免用“危险”泛指 P0/P1。 |
| UI-CONS-04 | 中 | “未接入”状态在不同段落中被归为未知、红色或灰红。 | 用户可能误判未接入是数据未知、配置缺失还是故障异常。 | 建议拆成三类：未接入=灰红/需接入；采集异常=红；未知/无返回=灰。应用接入列表、应用详情、空态统一该语义。 |
| UI-CONS-05 | 中 | 按钮层级口径略冲突。视觉规范和核心页将“查询”作为筛选区主按钮，配置页 2.2 将“查询”列为次按钮。 | 筛选表单与配置列表的主操作视觉权重可能不一致。 | 统一规则：筛选区“查询”为主按钮；页面级“新建/保存并启用”为主按钮。同一区域最多一个主按钮。 |
| UI-CONS-06 | 中 | 表格密度有全局规范，但配置页对列表行高、单元格内距、操作列收敛规则引用不足。 | 配置类表格可能比核心排障页更松散或操作按钮过多。 | 配置页补充“继承表格规范：表头 40px，行高 40/44px，单元格左右 12px，超过 3 个行操作收起”。 |
| UI-CONS-07 | 中 | 日志上下文默认行数有 20 与 50 两种口径。产品原型补充态写默认前后 20 行，高保真核心页写默认 50 行。 | 影响日志抽屉高度、查询成本和用户预期。 | 建议统一为默认前后 50 行，提供 10/20/50 可选；如考虑性能，默认 20 行需同步核心页验收点。 |
| UI-CONS-08 | 高 | 高保真页面说明未完整覆盖产品原型中的应用列表、服务器列表、告警列表、指标查询等列表/查询页。组件文档有规范，但缺少页面级高保真说明。 | 若直接进入全量设计稿，列表筛选、批量操作、状态汇总、导出受控和权限空态可能靠设计师临场补齐。 | 新增或补充 `list-and-states-high-fidelity.md`，覆盖应用列表、服务器列表、告警列表、指标查询、通用状态页。 |
| UI-CONS-09 | 中 | 状态文案局部不一致，例如“当前授权范围内暂无待处理问题”“当前没有未恢复告警”“暂无可查看数据”等相近场景缺少统一文案库。 | 空态文案在设计稿中容易出现语气和操作入口不一致。 | 在组件文档中增加“状态文案字典”，按无匹配、无授权、未接入、无告警、无日志、无指标分别固化标题、辅助说明、主操作。 |
| UI-CONS-10 | 中 | 组件命名基本一致，但“指标趋势”和产品原型中的“指标查询”边界未完全说明。 | 用户和设计师可能不清楚一级导航“指标中心”下是通用查询页还是告警上下文趋势页。 | 明确：指标趋势为上下文证据页，指标查询为通用查询页；二者共享图表组件、筛选器与导出受控规范。 |
| UI-CONS-11 | 中 | 响应式策略覆盖了核心页，但配置页复杂抽屉、权限选择器、值班组选择器在 1024px 以下的处理不足。 | 小屏或窄屏办公环境中，960px 抽屉和双栏选择器可能不可用。 | 补充配置页响应式：960px 抽屉在窄屏改 90vw，双栏/三栏选择器纵向堆叠，底部操作固定。 |
| UI-CONS-12 | 低 | 可访问性要求在组件评审清单中完整，但页面文档中没有反向引用。 | 设计稿标注阶段容易漏掉焦点态、键盘顺序、图标按钮可读标签。 | 在各页面验收点增加“继承组件可访问性要求”，尤其图标按钮 tooltip、状态非颜色表达、弹窗/抽屉焦点管理。 |

## 5. 建议修正优先级

### P0：进入全量设计稿前必须统一

1. 统一视觉 token，以 `visual-system.md` 为唯一来源，清理核心页和配置页中的散色值。
2. 统一 P0/P1/P2/P3、正常/预警/异常/严重/未知/未接入/采集异常的颜色与文案映射。
3. 补齐列表/状态类高保真页面说明，至少覆盖应用列表、服务器列表、告警列表、指标查询和通用状态页。

### P1：核心链路设计稿绘制时同步修正

1. 统一左侧导航宽度、表格行高、筛选区按钮层级。
2. 统一日志上下文默认行数与可选项。
3. 建立空、加载、异常、无权限、导出受控文案字典。
4. 明确“指标查询”和“指标趋势”的页面边界与复用组件。

### P2：设计标注和前端实现前补充

1. 配置类复杂抽屉和选择器补充响应式说明。
2. 各页面验收点补充可访问性引用。
3. 将状态标签、按钮、表格、图表、日志行整理为设计组件命名表，便于 Figma 组件库和前端组件命名一致。

## 6. 是否适合监控排障平台

结论：适合。

理由如下：

- 首页不是装饰性驾驶舱，而是以待处理问题、P0/P1、异常对象、负责人、日志/指标入口为首屏核心。
- 告警详情强调触发值、阈值、持续时间、关联日志、通知记录和处理记录，符合排障证据链。
- 日志查询先看错误聚合，再看明细和上下文，适合高压故障定位。
- 应用详情拆分指标源、日志源、Trace 源接入状态，能避免“没数据被误判为正常”。
- 权限与脱敏贯穿列表、详情、搜索、导出、URL 直访，符合企业内部平台安全要求。
- 视觉风格克制，高密度表格、弱分割线、局部骨架和模块内异常提示适合长时间值班使用。

## 7. 最终验收意见

本轮 UI 一致性评审给出“有条件通过”。

核心排障链路和配置管理链路可以进入设计稿绘制，但建议先按 P0 修正项完成一次文档口径收敛。若项目计划是全量页面同时出高保真设计稿，则 UI-CONS-01、UI-CONS-03、UI-CONS-04、UI-CONS-08 应视为阻塞项；若采用核心链路先行，则这些问题不阻塞首批页面开画，但必须在组件库和第二批页面绘制前关闭。
